# Public browser simulation on Cloudflare Pages

The public demo runs the scripted fixture entirely in the visitor's browser.
It needs no backend, sign-in, AWS account, paid model, database, or private file.
The Python API and hardened invite-only Compose deployment remain available
separately; see [deployment.md](deployment.md).

## Select execution explicitly

The default is `api`, including `npm run dev` and `npm run build`. API failures
show an error and never select browser execution. To build the public demo:

```bash
cd frontend
npm ci --ignore-scripts
npm run build:demo
```

`build:demo` uses the tracked, non-secret `.env.demo` setting
`VITE_BEACON_EXECUTION_MODE=browser-demo`. Alternatively, set that build variable
explicitly and run `npm run build`. Unsupported mode values fail configuration.
To run a browser demo locally during development, use `npm run dev -- --mode demo`.
Never put secrets in `VITE_` variables: build settings and browser code are public.

Browser runs identify themselves as **Browser simulation**. JSON reports carry
`execution_source: "browser-simulation"`; every event carries the matching source.
Markdown reports include that provenance and the AWS-enforcement limitation.
Old schema-v1 API exports still import, while mixed or unknown sources, extra
fields, live model/AWS claims, altered hashes, inconsistent measurements,
credential patterns, and oversized input/imports are rejected. Imported source
claims are unverified; strict validation is not a signature or proof of origin.

All bundled files, including fictional payroll, can be inspected by visitors.
The browser permission checks illustrate access limits; they are not a real
security boundary against the visitor or genuine AWS permission enforcement.
Use fictional data only. Documents, captures and imported reports remain in
memory; only the user's theme preference is persisted. Exports include inputs
and answers. Nothing is uploaded by comparison, import, or replay.

## Verification

```bash
.venv/bin/python scripts/check-browser-parity.py --check
cd frontend
npm audit --audit-level=high
npm run test
npm run test:e2e
npm run test:e2e:demo
```

The API browser suite needs the local Python virtual environment. The demo suite
starts only a static server for the built assets, applies the same `_headers`
file used by Pages, and does not start an API. It checks desktop/mobile behavior,
walkthrough, all outcomes, edits, graph/replay, JSON/Markdown exports, unverified
imports, invalid input, themes, keyboard use, reduced motion, accessibility,
browser errors, CSP violations, and absence of `/api/` and `/oauth2/` calls.

34 parity cases compare browser answers, measurements and tool traces against
expectations generated by the independent Python engine. CI checks that those
expectations remain current. Regenerate them only after reviewing a deliberate
engine change with `scripts/check-browser-parity.py`.

Source maps are explicitly disabled. Zod's optional code generation is disabled
so schema validation works without `unsafe-eval`. The Pages `_headers` policy
allows scripts/fonts/images from this origin, blocks application connections,
framing, workers, forms, objects and base overrides, and permits inline styles
needed by React Flow and Motion. No analytics, external fonts or paid services
are configured. Never upload diagnostic traces or the whole repository as assets.
Both build modes include the React Bits and IBM Plex font licenses under
`dist/licenses/`. The deployed-URL suite checks that those notices are served
unchanged; keep them in the uploaded build.

## First Pages release

1. Commit and push the finished changes; keep the repository private.
2. Wait for the exact commit's complete `Verify private simulation` workflow,
   including `Verify public browser demo`, to pass.
3. In Cloudflare Workers & Pages, continue to the Pages workflow, connect GitHub,
   and select only the Beacon repository in the GitHub app authorization.
4. Select `main`, root directory `frontend`, build command `npm run build`,
   output directory `dist`, and build variables `NODE_VERSION=24` and
   `VITE_BEACON_EXECUTION_MODE=browser-demo`. Set both production and preview
   variables if enabling previews. Leave Web Analytics disabled.
5. Deploy the verified commit. Use the provided HTTPS `pages.dev` domain.
6. Confirm the deployed commit in Pages and test that URL before sharing it:

```bash
cd frontend
BEACON_DEMO_URL=https://ACTUAL_PROJECT.pages.dev npx playwright test --config playwright.demo.config.ts
```

No custom domain is required. The current Free plan provides 500 builds/month:
https://developers.cloudflare.com/pages/platform/limits/.
The `_headers` file belongs in the build output and applies to static responses:
https://developers.cloudflare.com/pages/configuration/headers/.

Enable MFA on the GitHub and Cloudflare operator accounts. Account credentials
and MFA enrollment stay with the account owner; they are not application data.

## Later releases and rollback

Cloudflare's Git integration normally starts builds on pushes independently of
GitHub verification. After the first successful deployment, disable automatic
production and preview deployments in the Pages branch deployment controls if
keeping manual releases. Wait for verification for each new commit, then trigger
its deployment manually. For future automation, use a separate deployment step
after verification, a least-privilege credential kept in GitHub encrypted secrets,
and never credentials in this repository or frontend.

Retain the previous successful Pages deployment. If a release fails deployed-URL
acceptance, use Pages rollback to that successful version and retest the public
URL. A WSL Docker manifest does not qualify a Pages release. The Compose release
gate and real-provider acceptance apply only to the separate private API host.

Git integration cannot be added to a Direct Upload project later; create a new
Git-integrated project if changing upload models:
https://developers.cloudflare.com/pages/get-started/direct-upload/.
